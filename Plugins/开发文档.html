00先建立三个认知

0.1插件是一个独立的 .NET 程序，跑在 MCO 的进程里

插件编译成自己的 dll，由宿主用 AssemblyLoadContext 隔离加载，和主程序同进程、 权限与主程序完全相同——它能读写文件、联网、操作窗口。所以装一个插件等于 把主程序的权限交给它，安装即信任。反过来说：你自己写的插件想做什么都可以做， 不需要「申请权限」这个环节。

0.2契约是唯一官方接口，永远不要引用主程序 exe

宿主暴露给插件的全部能力都在契约程序集 MinecraftChatOverlay.Plugin.Abstractions.dll 里 （源码是 Plugins/Abstractions/PluginApi.cs，一个文件，两百多行）。 插件的 csproj 只引用它，绝不要引用主程序 exe——那会让你绑死在某个内部实现上， 主程序一改你就碎，而且宿主根本不保证内部类型可访问。

⛔
铁律一：插件工程里只出现 ProjectReference 或 Compile Include 到契约（Abstractions），任何情况下都不引用主程序 exe / 主程序工程。 需要「和宿主一样的界面」不是靠引用它，而是靠第 6 章的资源键。

契约的版本号是 PluginApi.Version（当前 = 1）。 宿主只加载 ApiVersion 完全相同 的插件，不匹配直接拒装并说明原因。 契约演进的原则是只增不减不改签名——已发布插件不能因为宿主升级而碎。

0.3宿主管生杀，插件要经得起「被处理」

  • Initialize 抛异常 → 插件被标成「加载失败」，主程序不受影响；
  • 页面 ContentFactory 抛异常 → 该页显示出错信息，主程序不受影响；
  • Shutdown 可能被调用多次（禁用、卸载、退出都会调）→ 必须写成幂等的；
  • 「禁用」≠「卸载」：禁用只是不再调用你的页面与消息事件，dll 还在内存里；卸载会删掉你的整个数据目录。
⚠️
铁律二：自己开的窗口、定时器、线程、事件订阅，全部要在 Shutdown 里收干净。 收不干净的典型症状：插件明明禁用了，悬浮窗还飘在游戏上；日志里还在刷消息。

1.3插件本体

C# · MyFirstPlugin.cs
using MinecraftChatOverlay.Plugin;

public sealed class MyFirstPlugin : IPlugin
{
    private IPluginHost? _host;

    public string Id => "yourname.myfirstplugin";      // 稳定唯一，装插件/存配置都靠它
    public string DisplayName => "我的第一个插件";

    public void Initialize(IPluginHost host)
    {
        _host = host;

        // 订阅聊天消息（注意：事件在宿主 UI 线程上触发，别做耗时操作）
        host.ChatLineReceived += line =>
        {
            if (line.Raw.Contains("gg"))
            {
                host.ShowToast("有人 gg 了：" + line.Raw);
            }
        };

        host.Log("[MyFirst] 已装载");

        // 注册一个导航页（表单式：宿主负责画，插件只交数据）
        host.RegisterPage(new PluginPage
        {
            Title = "我的第一个插件",
            Description = "收到含关键词的消息时弹提示。",
            Fields =
            {
                new PluginField
                {
                    Key = "keyword",
                    Label = "关键词",
                    Kind = PluginFieldKind.Text,
                    Text = "gg",
                    Hint = "消息里包含这个词就弹提示",
                    Changed = f => host.ShowToast("关键词已改为：" + f.Text),
                },
            },
            Actions =
            {
                new PluginAction
                {
                    Label = "测试一条提示",
                    Primary = true,
                    Invoke = () => { host.ShowToast("这是测试提示"); return "已弹出"; },
                },
            },
        });
    }

    public void Shutdown()
    {
        // 这里必须幂等：退订事件、关定时器、关窗口。最小插件没开任何东西，留空即可。
    }
}
💡
实现类必须是 public、非抽象、有公开无参构造函数，否则宿主 new 不出来。 入口类不写进 plugin.json 时，宿主会在 dll 里自动找「唯一实现 IPlugin 的公开类」； 实现类有多个时必须用 Entry 指明（见第 2 章）。

02plugin.json 完整规范

plugin.json 是插件包的身份证+说明书，作者手写。宿主解析时很宽容： 字段名大小写不敏感、允许 // 注释、允许尾逗号。装不上的第一排查对象就是它。

字段类型必填说明
idstring✅ 稳定唯一 id，形如 goldiamond.keydisplay（作者名.插件名）。 决定安装目录名，也是「禁用列表」的键。发布后不要改——改了等于另一个插件。
namestring✅界面显示名。
versionstring✅插件自己的版本号，作者自定（建议 semver）。
authorstring➖作者名。
descriptionstring➖一句话说明。
apiVersionint✅ 要求的契约版本。必须等于 PluginApi.Version（当前 1），否则拒装。
entrystring➖ 入口类型全名（含命名空间）。不写就在 dll 里自动找唯一实现 IPlugin 的公开类； 实现类有多个、或不想被自动扫描时才需要写。
assemblystring➖ 主 dll 文件名（相对插件目录）。不写就取目录里第一个非契约程序集的 dll。
capabilitiesstring[]建议写 这个插件会做什么（读日志/联网/操作窗口/轮询键盘……）。 安装确认框展示给用户看，是「知情同意」用的——如实写，别含糊。

数据放哪

位置路径用途
安装目录%APPDATA%\MinecraftChatOverlay\plugins\<id>\ 宿主释放 zip 的地方。插件只读这里（别往回写）。
数据目录%APPDATA%\MinecraftChatOverlay\plugin-data\<id>\ 插件自己的可写目录（即 host.PluginDirectory）。 配置、图片、日志都放这。卸载插件时整个目录会被删掉——别放用户可能想留下的东西。

03生命周期

一个插件从生到死经过这些节点：

安装 zip ──▶ 解压校验 ──▶ Initialize(host) ──▶ 运行中 ──┬─▶ Shutdown() ─▶ 禁用（dll 还在）
   （ApiVersion 必须相等）   │  注册页面/订阅事件/读配置/开窗口          │
                            └─▶ 页面被打开时才调 ContentFactory      ├─▶ Shutdown() ─▶ 卸载（删数据目录）
                                                                    └─▶ Shutdown() ─▶ 程序退出

3.1Initialize 里适合做什么

  • 读配置（PluginSettingsFile.Load，见第 7 章）；
  • 注册页面（一个插件只能注册一个，重复调用以最后一次为准）；
  • 订阅事件（ChatLineReceived 等）；
  • 开常驻资源：定时器、悬浮窗（按需：也可以等开关打开再开）；
  • 页面预检（自绘页面推荐，见 11.2——XAML 是运行期解析的，编译过 ≠ 能解析）。

Initialize 抛异常会被宿主吞掉，插件标记为「加载失败」并展示异常信息，主程序不受影响。 所以插件自己要做好防御：IO、网络、反射都 try/catch，失败要 host.Log 说明。

3.2Shutdown 必须幂等

C#
private bool _shutdown;

public void Shutdown()
{
    if (_shutdown) return;          // 幂等闸门：可能被调多次
    _shutdown = true;

    _cycleTimer?.Stop();               // 停定时器
    _overlay?.Close();                 // 关自己的窗口（Close 幂等，重复调无害）
    if (_host is not null)
    {
        _host.ChatLineReceived -= OnChatLine;   // 退订事件
    }
}

4.4页面数据模型（表单式用，详见第 5 章）

类型要点
PluginPage Title（导航文字，必填）/ Description（页头说明）/ Fields（字段列表）/ Actions（按钮列表）/ ContentFactory（自绘页面，可选）/ StatusText（页头状态行，可选，宿主每秒问一次）。

4.5PluginSettingsFile（配置小工具）

C#
// 读：文件不存在或坏了 → 返回默认值（new T()），不抛异常
var settings = PluginSettingsFile.Load<MySettings>(host.PluginDirectory);

// 写：写失败不抛异常（配置丢了不该让插件崩）。缩进 JSON。
PluginSettingsFile.Save(host.PluginDirectory, settings);

// 默认文件名 settings.json，可以换：
PluginSettingsFile.Save(host.PluginDirectory, settings, "layouts.json");

约束：where T : new()，即配置类必须有公开无参构造。 新版本加字段时老配置文件里没有 → 反序列化用默认值兜底，天然平滑升级。

05页面系统

插件页面有两种做法：表单式（交数据，宿主画——零 XAML，天生和宿主长一个样）和 自绘式（ContentFactory 返回一个 WPF 控件，想怎么画怎么画）。先表单式，表达不了再自绘。

5.1表单式：字段 + 按钮

C#
host.RegisterPage(new PluginPage
{
    Title = "我的插件",
    Description = "这页是干什么的，一句话。",
    StatusText = () => _running ? $"运行中 · 已处理 {_count} 条消息" : null,
    Fields =
    {
        new PluginField { Key="enabled", Label="启用", Kind=PluginFieldKind.Toggle,
            Bool=true, Hint="关掉后停止处理消息",
            Changed = f => { _running = f.Bool; SaveSettings(); } },

        new PluginField { Key="interval", Label="刷新间隔", Kind=PluginFieldKind.Slider,
            Number=40, Minimum=10, Maximum=500, Step=10, Suffix=" ms",
            Changed = f => { _timer.Interval = TimeSpan.FromMilliseconds(f.Number); } },

        new PluginField { Key="target", Label="目标窗口", Kind=PluginFieldKind.Select,
            OptionsProvider = () => host.GetGameWindows()
                .Select(w => new PluginOption(w.Handle.ToString(), w.Title)).ToList(),
            OptionsRefreshSeconds = 5,
            Changed = f => SelectWindow(f.SelectedKey) },

        new PluginField { Key="note", Label="备注", Kind=PluginFieldKind.Text,
            Text="" },

        new PluginField { Key="info", Kind=PluginFieldKind.ReadOnly,
            Text="当前版本 1.0.0，作者 yourname。" },
    },
    Actions =
    {
        new PluginAction { Label="立即刷新", Primary=true,
            Invoke = () => { DoRefresh(); return "已刷新"; } },
        new PluginAction { Label="重置统计",
            Invoke = () => { _count = 0; return null; } },
    },
});

要点：

  • 值变化即回调 Changed，插件自己负责存盘（配第 7 章的防抖保存）；
  • 字段的 Enabled 和 StatusText 宿主每秒刷新一次—— 做成「读当前状态的委托」而不是设一次就完；
  • Select 的候选用 OptionsProvider，配 OptionsRefreshSeconds 可定时重取 （比如目标窗口列表会变）。

5.2自绘式：ContentFactory

表单表达不了的（规则列表、拖拽、实时预览、自由排版），用 ContentFactory 返回自己的控件：

C#
host.RegisterPage(new PluginPage
{
    Title = "我的插件",
    ContentFactory = () => new MyPage(this),   // 返回 FrameworkElement
    StatusText = BuildStatus,
});
  • 返回的控件跑在宿主 UI 线程上，抛异常会被宿主拦住、页面显示出错信息——和 Initialize 一样要做好防御；
  • 页面类通常是 UserControl（.xaml + .xaml.cs）；
  • ContentFactory 每次打开页面都会调用——页面里持有的引用（_page 字段）要记得跟随更新，别抱着旧实例；
  • 想要和宿主一样的观感，用 DynamicResource 引用宿主主题资源——这正是下一章的全部内容。
⚠️
预检习惯：页面 XAML 是运行期解析的，编译通过不代表能解析。在 Initialize 里 try { _ = new MyPage(this); host.Log("页面预检通过"); } catch (Exception ex) { host.Log("预检失败：" + ex); }， 问题在装载时就暴露，不用等用户点开页面看白屏。（见 11.2）

private void FontSizeSlider_Changed(object sender, RoutedPropertyChangedEventArgs<double> e)
{
    // _loading=true 表示是程序回填触发的，跳过处理（详见第 7 章）
    if (_loading) return;

    int value = (int)Math.Round(e.NewValue);
    FontSizeText.Text = value.ToString();      // 数值实时跟

    ScheduleSave();                             // 防抖存盘，见 7.2
    ApplyAppearance();                          // 让悬浮窗立刻生效
}

// 程序回填（打开页面/切换选中项时）：
private void PushSettingsToUi()
{

    {
        FontSizeSlider.Value = _settings.FontSize;   // 这会触发 ValueChanged，被闸门挡住

// hex → Color 的宽容解析（配置可能被手改坏，永远给兜底）
private static Color ParseColor(string? text, Color fallback)
{
    if (!string.IsNullOrWhiteSpace(text))
    {
        try {
            var c = (Color)ColorConverter.ConvertFromString(text.Trim());
            return Color.FromArgb(255, c.R, c.G, c.B);   // 透明度单独管理，这里吃掉 A
        }
        catch { }
    }
    return fallback;
}

取色窗：优先宿主同款 ColorDialog，自绘只做兜底

💡
宿主内置模块（「击杀反馈」页选边缘颜色）用的就是 WinForms 的 System.Windows.Forms.ColorDialog —— 左边一排预设、右边色域随便调、还能自定义。 插件直接用同一款，观感跟宿主完全一致，用户零学习成本。KeyDisplay 实测在插件上下文里能正常弹出。
⚠️
两个真实的坑，别踩：
① CS0104 撞名：开 WinForms 会引入 System.Drawing / System.Windows.Forms 的隐式 using， 跟 WPF 的 Brush / Point / MouseEventArgs 全部撞名。一律写全限定名 （System.Windows.Forms.ColorDialog、System.Drawing.Color）， 或者像 KeyDisplay 那样用 using Color = System.Windows.Media.Color 显式钉住。
② 调色盘不支持 alpha：它返回的 A 恒为 255，直接拿来用会把用户设的透明度抹平。 只取 RGB、A 用原值拼回去，透明度交给旁边那条独立滑块（宿主自己也是这个组合）。

统一入口 + 兜底的完整写法（KeyDisplay 的 ColorPickerWindow.Pick，逐条对齐宿主 MainWindow.PickColorHex）：

C# · Pick：宿主同款优先，自绘兜底
/// 统一入口：能用系统调色盘就用它，调不起来退回自绘窗
public static string Pick(Window? owner, string current)
{
    return TryPickWithSystemDialog(current, out var picked) ? picked : PickWithOwnWindow(owner, current);
}

/// 三个关键点逐条对齐宿主 MainWindow.PickColorHex：
///   FullOpen = true —— 一打开就展开色域，不用再点「规定自定义颜色」
///   不设 AnyColor —— 宿主也没设，有 FullOpen 就能调任意色
///   显式保留原 A —— 调色盘的 A 恒为 255，照抄会抹掉透明度
private static bool TryPickWithSystemDialog(string currentHex, out string result)
{
    result = currentHex;
    try
    {
        var start = Parse(currentHex);
        using var dialog = new System.Windows.Forms.ColorDialog
        {
            FullOpen = true,
            ShowHelp = false,
            Color = System.Drawing.Color.FromArgb(start.A, start.R, start.G, start.B),
        };

        if (dialog.ShowDialog() == System.Windows.Forms.DialogResult.OK)
        {
            var c = dialog.Color;
            var picked = Color.FromArgb(start.A, c.R, c.G, c.B);  // ★ A 用原来的
            result = FormatHex(picked);
        }
        return true;      // 能弹出来就算成功（点取消 = 保持原值）
    }
    catch { return false; }   // 调不起来 → 走兜底
}

/// hex 格式跟宿主一致：纯色省掉 A（#RRGGBB），半透明才写全（#AARRGGBB）。
/// 页面写回颜色也走这里 —— 别两处各写一遍格式化。
internal static string FormatHex(Color color) =>
    color.A == 0xFF
        ? $"#{color.R:X2}{color.G:X2}{color.B:X2}"
        : $"#{color.A:X2}{color.R:X2}{color.G:X2}{color.B:X2}";

7.2防抖保存（别每拖一格滑条写一次盘）

C# · ScheduleSave 模式
private System.Windows.Threading.DispatcherTimer? _saveTimer;

/// 值变了先标记，500ms 内没有新变化才落盘。滑条狂拖时不会每格写一次盘。
private void ScheduleSave()
{
    if (_saveTimer is null)
    {
        _saveTimer = new System.Windows.Threading.DispatcherTimer
        {
            Interval = TimeSpan.FromMilliseconds(500),
        };
        _saveTimer.Tick += (_, _) => { _saveTimer.Stop(); SaveSettings(); };
    }
    _saveTimer.Stop();
    _saveTimer.Start();      // 重新计时：合并这 500ms 内的所有变化
}

public void SaveSettings()
{
    try { PluginSettingsFile.Save(_host!.PluginDirectory, Settings); }
    catch { }
}

7.4自检/探针不得污染用户配置（血泪教训）

如果插件内置自检（推荐，见 11.3），自检会改配置去验证行为。必须三件套防护， 否则用户配置会被探针值刷掉——真实事故：反复跑自检后，用户的「整体大小」被永久改成 50%。

C# · 自检防污染三件套
private bool _suppressSave;

// ① 写盘总闸：自检期间任何路径的保存都被吞掉
public void SaveSettings()
{
    if (_suppressSave) return;
    try { PluginSettingsFile.Save(_host!.PluginDirectory, Settings); }
    catch { }
}

private void RunSelfTestIfRequested()
{
    _suppressSave = true;                          // ② 总闸拉起
    try { RunSelfTestBody(); }                        //    自检主体：改配置→验证→try/finally 内还原
    finally
    {
        _suppressSave = false;
        // ③ 结束后从磁盘重载（不是保存！）——自检中途炸掉时内存里残留探针值，
        //    此时保存反而落盘脏值；重载则无条件回到用户真实的配置。
        try { Settings = PluginSettingsFile.Load<KeyDisplaySettings>(_host!.PluginDirectory); }
        catch { }
    }
}

自检主体里改配置同样要 try/finally 还原——总闸是最后防线，不是免还原的理由。

using System.Runtime.InteropServices;
using System.Windows.Interop;

public partial class OverlayWindow : Window
{
    private const int GWL_EXSTYLE = -20;
    private const int GWLP_HWNDPARENT = -8;
    private const int WS_EX_NOACTIVATE  = 0x08000000;   // 永不激活
    private const int WS_EX_TRANSPARENT = 0x00000020;   // 鼠标穿透
    private const int WS_EX_TOOLWINDOW = 0x00000080;   // 不进任务栏/Alt+Tab

    [DllImport("user32.dll")] private static extern int GetWindowLong(IntPtr hWnd, int nIndex);
    [DllImport("user32.dll")] private static extern int SetWindowLong(IntPtr hWnd, int nIndex, int dwNewLong);

8.3不抢焦点（最重要的一条）

悬浮窗一旦抢焦点，Minecraft 立刻失焦弹 ESC 菜单——用户视角就是「游戏莫名其妙暂停了」。

C#
private IntPtr _handle;
private bool _clickThrough = true;

protected override void OnSourceInitialized(EventArgs e)
{
    base.OnSourceInitialized(e);
    _handle = new WindowInteropHelper(this).Handle;
    ApplyExtendedStyles();
    DetachFromOwner();
}

private void ApplyExtendedStyles()
{
    if (_handle == IntPtr.Zero) return;

    var current = GetWindowLong(_handle, GWL_EXSTYLE);
    var wanted = current | WS_EX_NOACTIVATE;        // ← 核心：Win32 层永不激活

    if (_clickThrough)
        wanted |= WS_EX_TRANSPARENT;                 // 穿透开关
    else
        wanted &= ~WS_EX_TRANSPARENT;

    if (wanted != current)
        SetWindowLong(_handle, GWL_EXSTYLE, wanted);
}
⚠️
为什么 XAML 上的 ShowActivated="False" 不够：它只在窗口第一次显示时可靠； 复用型窗口（隐藏再显示）、或某些交互路径下，WPF 仍可能激活它。 WS_EX_NOACTIVATE 是 Win32 层的保证——点了也永远不成为前台窗口。两个都设。

8.4真鼠标穿透

IsHitTestVisible="False" 只管 WPF 层的命中测试——窗口在系统眼里依然可点， 全屏游戏里光标照样现形。真穿透必须 WS_EX_TRANSPARENT（上节代码已含开关）。 注意：穿透模式下窗口收不到鼠标 → 拖不动。所以宿主的惯例是——

  • 位置以设置为准（穿透时不能拖，天经地义）；
  • 页面里给一个「拖动定位」ToggleButton（SmallPrimaryToggleButtonStyle）， 开着时关掉穿透允许拖动（OnMouseLeftButtonDown → DragMove），关掉恢复穿透并记下位置。

8.5置顶的残酷真相与任务栏

  • Topmost 不是万能：游戏真全屏（独占）模式下任何窗口都压不住；无边框窗口模式下 Topmost 通常有效。 你动了别的窗口层级之后，记得调 host.ReassertOverlayTopmost()，别让宿主的聊天悬浮窗被压下去。
  • 不进任务栏/Alt+Tab 用 WS_EX_TOOLWINDOW。不能只靠 ShowInTaskbar="False"—— 那个的 WPF 实现是「给窗口挂一个隐藏的所有者」，而悬浮窗恰恰要清所有者（见下），两个需求打架，Win32 说了算：
C# · 清所有者 + 工具窗
/// 清所有者：宿主主窗口最小化时，「被拥有的窗口」会跟着不可见——悬浮窗不能有主人。
public void DetachFromOwner()
{
    try
    {
        Owner = null;
        if (_handle == IntPtr.Zero) return;

        // GWLP_HWNDPARENT 清 Win32 层所有者
        if (IntPtr.Size == 8)
            SetWindowLongPtr64(_handle, GWLP_HWNDPARENT, IntPtr.Zero);
        else
            SetWindowLongPtr32(_handle, GWLP_HWNDPARENT, IntPtr.Zero);

        // WS_EX_TOOLWINDOW：不占任务栏、不进 Alt+Tab
        var style = GetWindowLong(_handle, GWL_EXSTYLE);
        if ((style & WS_EX_TOOLWINDOW) == 0)
            SetWindowLong(_handle, GWL_EXSTYLE, style | WS_EX_TOOLWINDOW);
    }
    catch { }
}

// SetWindowLongPtr 的 64/32 位包装：
[DllImport("user32.dll", EntryPoint = "SetWindowLongPtr")]
private static extern IntPtr SetWindowLongPtr64(IntPtr hWnd, int nIndex, IntPtr dwNewLong);
[DllImport("user32.dll", EntryPoint = "SetWindowLong")]
private static extern int SetWindowLongPtr32(IntPtr hWnd, int nIndex, int dwNewLong);
⛔
WS_EX_TOOLWINDOW 的隐藏代价：OBS 抓不到这个窗口。 OBS「窗口捕获」枚举窗口时会过滤掉工具窗 —— 悬浮窗设了 TOOLWINDOW 就**根本不出现在 OBS 的窗口列表里**， 直播用户想抓按键显示/歌词窗抓不到。 判断依据（2026-10-04 实证）：宿主自己的聊天悬浮窗没设 TOOLWINDOW （它保留所有者，ShowInTaskbar="False" 就够），所以 OBS 一直能看到它。

解法：OBS 直播模式开关（KeyDisplay / NeteaseLyrics 都是这么做的）—— 设置加一个 ObsMode（默认关），开着时动态摘掉 TOOLWINDOW：

C# · SetObsMode：动态切换（不用重建窗口）
/// true = 摘掉 TOOLWINDOW（OBS 列表能看到、能抓）；false = 恢复（不占任务栏/Alt+Tab）
public void SetObsMode(bool on)
{
    var handle = new WindowInteropHelper(this).Handle;
    if (handle == IntPtr.Zero) return;

    var style = GetWindowLong(handle, GWL_EXSTYLE);
    var wanted = on ? (style & ~WS_EX_TOOLWINDOW) : (style | WS_EX_TOOLWINDOW);
    if (wanted != style) SetWindowLong(handle, GWL_EXSTYLE, wanted);
}

三个必须想清楚的点：

  • 开着的代价：所有者已被清（悬浮窗必须独立存活），ShowInTaskbar="False" 失效， 摘掉 TOOLWINDOW 后窗口会出现在任务栏和 Alt+Tab 里。直播场景基本无感，但要写进设置页文案让用户自己选；
  • 任务栏右键"关闭窗口"：窗口出现在任务栏后用户能右键关它 —— 必须像 KeyDisplay 那样 把 Closing 拦成 Hide（args.Cancel = true）， 不然窗口实例被关废（WPF 不允许 Show 一个已 Close 的窗口）；
  • 切换即时生效：改样式位就行，不用重建窗口。挂在 ApplySettings / SyncWindowState 这类统一同步点上。
💡
顺带说明透明窗黑屏问题：WPF 的 AllowsTransparency="True" 窗口是分层窗口， OBS 默认的 BitBlt 捕获方式抓出来是黑的 —— 但现代 OBS 的「Windows 10（1903+）」捕获方式（WGC）能正常抓。 所以 OBS 侧把窗口捕获的方法切到 WGC 即可，代码侧不用为黑屏做任何事。

8.7尺寸与阴影留白

DropShadowEffect 超出内容的部分会被窗口边缘切掉，所以窗口 = 内容 + 留白（Canvas Margin）。 而留白大小会随阴影参数变化——如果窗口 Left/Top 不动、只有留白变了，内容在屏幕上会漂 （「改个阴影大小，按键就移位」）。解法：位置一律按内容左上角记，留白变了反向补：

C# · 内容左上角对齐
// 摆位：存的 WindowLeft/Top 是「内容左上角」，窗口位置减掉当前留白
public void ApplyPosition(MySettings settings, bool force = false)
{
    if (_positioned && !force) return;
    Left = settings.WindowLeft - _shadowPadding;
    Top  = settings.WindowTop  - _shadowPadding;
    _positioned = true;
}

// 用户拖完：把窗口位置换算回「内容左上角」记进设置
public void RememberCurrentPosition(MySettings settings)
{
    settings.WindowLeft = Left + _shadowPadding;
    settings.WindowTop  = Top  + _shadowPadding;
}

// 阴影参数变了之后：重新对齐，内容纹丝不动
public void SyncPositionToContent(MySettings settings)
{
    if (double.IsNaN(Left) || double.IsNaN(Top)) return;
    Left = settings.WindowLeft - _shadowPadding;
    Top  = settings.WindowTop  - _shadowPadding;
}

8.10防出屏：窗口永远不许跑出屏幕

用户拖悬浮窗能拖到哪？默认答案是屏幕外任意远——WPF 的 DragMove() 不管这个，松手就停在那儿，出界的位置还会被存进配置，重启才被拉回来。 放大缩放、改阴影（留白变化）也会让窗口悄悄出界。 8.8 那个摆位示例只在启动时钳一次，运行中没人管。

正确的做法是四层钳制，全是同一个方法：

C# · 钳制方法（多显示器安全）
/// 用 VirtualScreen（全部屏幕的联合包围盒）而不是单屏 WorkArea：
/// 多显示器下副屏也能去，只拦「所有屏幕之外」。都是 DIP，跟 Left/Top 同单位。
public void ClampToVirtualScreen()
{
    var vsLeft = SystemParameters.VirtualScreenLeft;
    var vsTop  = SystemParameters.VirtualScreenTop;
    var vsRight  = vsLeft + SystemParameters.VirtualScreenWidth;
    var vsBottom = vsTop  + SystemParameters.VirtualScreenHeight;

    // ⚠ Math.Clamp 在 min>max 时抛异常 —— 窗口比屏幕还大的极端情况先判，对齐左上角
    if (ActualWidth <= vsRight - vsLeft)
        Left = Math.Clamp(Left, vsLeft, vsRight - ActualWidth);
    else
        Left = vsLeft;

    if (ActualHeight <= vsBottom - vsTop)
        Top = Math.Clamp(Top, vsTop, vsBottom - ActualHeight);
    else
        Top = vsTop;
}
挂哪管什么场景
拖动的每一帧（自绘拖动的 OnMouseMove 里）核心场景：拖动中窗口物理上出不了屏，而不是拖出去再弹回
ResizeToContent / Rebuild 之后放大缩放、改阴影 → 窗口变大 → 右/下缘出界
ApplyPosition（装载摆位）手改配置 / 换显示器之后，存的位置本来就在屏幕外
刷新 Tick 里顺手调一次分辨率变化、拔副屏 —— 出界后 16ms 内自动拉回；平时是同值赋值，零开销

拖动为什么弃用 DragMove：DragMove 是系统模态拖动，拖动期间你插不进手（没法在每一帧做钳制）。 自绘拖动的手感跟它完全一样（都是「鼠标相对窗口的抓取点不变」），但每一帧都在你手里：

C# · 自绘拖动（增量式，纯 DIP，无需 DPI 换算）
private bool _dragging;
private double _dragGrabX, _dragGrabY;

protected override void OnMouseLeftButtonDown(MouseButtonEventArgs e)
{
    base.OnMouseLeftButtonDown(e);
    if (!ClickThrough)
    {
        _dragging = true;
        var pos = e.GetPosition(this);   // 按下时鼠标在窗口内的坐标
        _dragGrabX = pos.X; _dragGrabY = pos.Y;
        CaptureMouse();                      // 鼠标出窗口也不中断
    }
}

protected override void OnMouseMove(MouseEventArgs e)
{
    base.OnMouseMove(e);
    if (!_dragging) return;

    var pos = e.GetPosition(this);
    // 增量公式：鼠标在窗口内偏了多少，窗口补多少 —— 不需要鼠标物理坐标（那要 DPI 换算）
    Left += pos.X - _dragGrabX;
    Top  += pos.Y - _dragGrabY;

    ClampToVirtualScreen();                  // ★ 每帧钳制，出不了屏
}

protected override void OnMouseLeftButtonUp(MouseButtonEventArgs e)
{
    base.OnMouseLeftButtonUp(e);
    EndDrag();                               // 清标志 + ReleaseMouseCapture，幂等
}
⚠
两个易漏的坑： ① 拖到一半被打开鼠标穿透（窗口从此收不到鼠标事件）—— UpdateTransparent 里要先 EndDrag()，不然 _dragging 挂在 true； ② 自绘拖动全程 try/catch 包住 —— 抛了同样留下脏状态。
💡
做成开关：保护性行为也别替用户做死 —— 加一个设置项（如 ClampToScreen，默认开），窗口加一个 ClampEnabled 属性， ClampToVirtualScreen() 开头判断它。想"一半藏在屏幕外"的用户关掉就行。 自检把开关两个方向都验：开着能钳、关着真的不钳（防止"关了还钳"的接错线）。
💡
自检怎么写：把窗口位置故意扔到屏幕外四个方向（左上 -5000、右下 +5000）， 调 ClampToVirtualScreen() 断言拉回；再把缩放临时拉到 8.0 让窗口必超屏幕， 断言对齐左上且不抛异常。位置的探针值由防污染三件套兜底（_suppressSave + 磁盘重载）， 不会污染用户配置。KeyDisplay 的「防出屏自检」就是这么验的。

9.2.1两种读法，怎么选

按键状态有两条路，先问自己「目标是不是走 Raw Input 的游戏」：

读法能读什么代价什么时候用
GetAsyncKeyState 轮询 桌面、浏览器、Minecraft（Java 版）等走正常消息队列的程序 几乎没有。零介入、不碰权限、卸载后什么都不剩 默认选它。绝大多数场景够用
WH_KEYBOARD_LL 低级键盘钩子 也能读走 Raw Input 的游戏（绝区零、原神这类引擎自管输入的） 全程介入每次按键；需要提权；杀软会多看两眼 目标明确是游戏，且轮询读不到时

为什么轮询读不到游戏：GetAsyncKeyState 读的是 Windows 消息队列里的按键状态。 游戏引擎（Unity/Unreal 那类）直接读键盘驱动的原始数据（Raw Input / DirectInput）， 不往消息队列塞 WM_KEYDOWN —— 操作系统根本不知道键被按了，轮询就永远是「没按」。

为什么钩子能读到：钩子挂的位置比消息队列更靠近硬件。 键盘驱动产生的事件先过一遍所有低级钩子，然后才分发给前台窗口或 Raw Input。 所以哪怕游戏绕过了消息系统，钩子也照样看得见。

⛔
键盘和鼠标是两个独立的钩子，必须各装一个。 WH_KEYBOARD_LL(13) 和 WH_MOUSE_LL(14) 互不相干 —— 装了键盘不等于鼠标也会过你的回调。漏了鼠标那个的表现很具体： 游戏里键盘格子亮了、鼠标格子不亮（桌面场景因为能降级轮询，看着是好的，所以很难察觉）。 项目里 KeyDisplay 就踩过这个坑（2026-10-03）。
⚠
钩子要生效，宿主必须以管理员权限运行。 Windows 的 UIPI 机制不允许低完整性级别的进程接收高完整性级别进程的输入。 游戏通常由启动器提权拉起，宿主不提权的话，钩子依然收不到它的按键 —— 表现是「换成了钩子，游戏里还是不亮」。设置页里要把这句话写给用户看。

9.2.2只读钩子怎么写（照抄这一段）

按键显示要的是「看」，不是「拦」。所以回调里只记状态、立刻放行。 下面这十条每条都会在出问题的时候让你查半天，一条都别省：

C# · 只读的低级键盘钩子
private const int WH_KEYBOARD_LL = 13;

// ① 委托必须存字段 —— 交给系统的是函数指针，托管侧没强引用会被 GC 回收，
//    回收后回调指向野地址，进程直接崩。这是本文件最容易踩的坑。
private LowLevelKeyboardProc? _proc;

// ② 装钩子必须在本进程 UI 线程上 —— 低级钩子靠宿主线程的消息循环派发回调，
//    在纯后台线程上装会「装成功但永远收不到回调」。
// ③ hMod 传 IntPtr.Zero 对 WH_KEYBOARD_LL 是正确的（不注入 DLL，所以不需要模块句柄）。
_hookHandle = SetWindowsHookEx(WH_KEYBOARD_LL, _proc, IntPtr.Zero, 0);

private IntPtr HookCallback(int nCode, IntPtr wParam, IntPtr lParam)
{
    // ④ 整段 try/catch 包住 —— 回调往外抛异常会一路穿到系统，后果不可控，
    //    而且异常本身就会导致钩子被摘。
    try
    {
        // ⑤ 别做任何耗时的事。系统给钩子回调的超时是 300ms（LowLevelHooksTimeout），
        //    超时一次 Windows 会【静默摘掉】这个钩子且不通知 —— 表现是「用着用着突然不亮了」，
        //    查不出任何报错。所以回调里只做一次状态位写入：不取锁、不做 IO、不碰 UI。
        if (nCode >= 0) { /* 只记「哪个键按下/松开」 */ }
    }
    catch { }

    // ⑥ ★ 必须 CallNextHookEx 放行。漏了这行 = 吞掉全系统按键，用户机器直接没法打字。
    //    这是整个文件最不能出错的一行。
    return CallNextHookEx(_hookHandle, nCode, wParam, lParam);
}

鼠标钩子：另一套消息和结构体

鼠标钩子的写法和键盘一样（超时意识、异常吞掉、必须放行），只有两处不同：

C# · 鼠标回调的消息映射
// ① 装的时候用 WH_MOUSE_LL(14)，回调委托是另一个类型
_mouseHookHandle = SetWindowsHookEx(WH_MOUSE_LL, _mouseProc, IntPtr.Zero, 0);

// ② 结构体完全不同 —— 别拿 KBDLLHOOKSTRUCT 去解析鼠标消息，会读到垃圾值
[StructLayout(LayoutKind.Sequential)]
private struct MsLlHookStruct
{
    public int PtX; public int PtY;      // 坐标 —— 键位显示不需要，别读，少读少一份隐私面
    public uint MouseData;                  // 判侧键用
    public uint Flags; public uint Time; public IntPtr DwExtraInfo;
}

// ③ 鼠标消息的 wParam 不是虚拟键码，要自己映射 —— 这样上层拿到的和键盘统一
int? vk = msg switch
{
    WM_LBUTTONDOWN or WM_LBUTTONUP => 0x01,   // VK_LBUTTON
    WM_RBUTTONDOWN or WM_RBUTTONUP => 0x02,   // VK_RBUTTON
    WM_MBUTTONDOWN or WM_MBUTTONUP => 0x04,   // VK_MBUTTON
    _ => null,
};

// ④ 侧键（XBUTTON）要读 mouseData 才知道是哪个：高位 1 = 侧键1，2 = 侧键2
var which = (xInfo.MouseData >> 16) & 0xFFFF;
vk = which switch { 1 => 0x05, 2 => 0x06, _ => null };

两个钩子共用一个虚拟键码状态位图就够了 —— 这样对上层（悬浮窗、CPS、自检） 接口仍然只有一个 IsDown(vk)，不用改。

💡
降级要分键盘鼠标判。万一只有键盘钩子装上了、鼠标钩子没装上， 鼠标键那半必须走轮询兜底，否则位图里没人写它、永远是"没按"。 按虚拟键码区间分（0x01~0x06 是鼠标键）即可。

回调里读什么、写什么

  • 读：wParam（消息类型：WM_KEYDOWN / WM_KEYUP / 含 Alt 的 SYS 版）和 KBDLLHOOKSTRUCT.VkCode（虚拟键码）。别的字段一律别碰；
  • 写：只写一个「按下/松开」的位。用位图（ulong[4]）而不是 HashSet——回调是高频路径，任何分配/哈希/扩容都可能把它拖过 300ms 线；
  • 绝对不要 return 1。那是「吞键」，属于键盘锁定/改键的活（见 AutoGg），不是按键显示该干的。

被静默摘掉怎么办

系统摘钩子不通知，所以得自己探活。EnsureAlive() 之类的健康检查 每 2 秒跑一次：发现句柄失效就重装，并记日志。 重装代价极小（两次 Win32 调用），比设计复杂的判活逻辑划算。KeyDisplay 就是这么做的。

隐私边界（写代码时要守住）

  • 只记按键的按下/松开状态位；时间戳只用于判断钩子是否还活着；
  • 不记录按键序列、不区分来源进程、不记窗口标题 —— 那就成键盘记录器了；
  • 不写任何文件；卸载时句柄释放、状态表清空；
  • capabilities 里如实写「安装了 WH_KEYBOARD_LL 钩子，只读取状态、不拦截、不记录」—— 别含糊其辞，用户有知情权。

9.2.3两种模式并存的写法

如果插件的用户群既有「桌面党」也有「游戏党」，别二选一，做成可切换的。 关键在于抽一层接口，让上层逻辑不关心底下用哪种方式：

C# · 读取层抽象
internal interface IKeyStateSource : IDisposable
{
    bool IsActive { get; }        // 钩子装失败时 false
    string Name { get; }          // 人话名字，日志/界面用
    bool IsDown(int virtualKey);     // 唯一的对外接口
}

// 轮询实现：无状态，Dispose 是空的
// 钩子实现：有句柄，Dispose 要 UnhookWindowsHookEx

// 全局出口 —— 调用方（悬浮窗刷新、CPS 采样、自检）只认这行，换实现不动它们
internal static IKeyStateSource _source = new PollingKeyStateSource();

internal static void SwitchSource(IKeyStateSource next)
{
    var old = Interlocked.Exchange(ref _source, next);   // 换引用是原子操作
    if (!ReferenceEquals(old, next)) old?.Dispose();
}

几个要注意的点：

  • 切换要即时生效，不用重启宿主。切到钩子就装、切回轮询就卸，路径要对称；
  • 切换是幂等的——模式没变就别卸了重装，白白摘掉一次钩子；
  • 装失败要退回轮询并改回设置。否则用户看到开关是「钩子」、实际在轮询， 会觉得莫名其妙（设置项要跟着回退，界面也要重新对齐）；
  • Shutdown 必须先卸钩子。留一个钩子比留一个定时器危险得多 —— 宿主都关了它还在跑的话，全系统按键都要过一遍你的回调；
  • 卸载路径必须幂等，重复调用安全。这是四条铁律之一；
  • 钩子没装成时，IsDown 要退回轮询，别让整个功能哑掉 —— 至少桌面场景还能用。
💡
参考实现：Plugins/KeyDisplay/ 里的 KeyStateSource.cs（两种实现 + 接口）、 VirtualKeys.cs（统一切换出口）、 KeyDisplayPlugin.cs 的 ApplyInputMode() / CheckHookHealth()。设置页的读取方式开关见 KeyDisplayPage.xaml，权限提示的实现见 KeyDisplayPlugin.IsProcessElevated。

9.3游戏交互：只做「读」和「飘窗」

  • 读：游戏日志（宿主已读好并解码，走 ChatLineReceived）、按键状态（轮询）、窗口列表（GetGameWindows）；
  • 飘窗：自己的悬浮窗爱怎么画怎么画；
  • 不注入：不往游戏进程写内存、不加载 mod、不 hook 游戏函数——这类能力本插件系统就不提供， 也不要自己用 P/Invoke 搞；
  • 改游戏画面只走「悬浮窗叠加」这一条路。

9.4性能红线

  • ChatLineReceived 在宿主 UI 线程触发——耗时操作（网络、文件、大量计算）会卡整个宿主界面。 要做就丢给 Task.Run，回 UI 再 Dispatcher.Invoke；
  • 40ms 级刷新定时器里别做重量级事（整树 Rebuild、大量分配）；高频路径只刷值不重建结构 （KeyDisplay 的教训：Rebuild 建树 / ApplyAppearance 轻刷新 / 每帧刷色，三条路径分开）；
  • 动画定时器停掉再改参数，别叠跑多个 DispatcherTimer 干同一件事。

9.5网络与隐私

  • 联网的插件在 capabilities 里写清楚「联网做什么、数据去哪」；
  • 不上传任何含用户身份的信息（路径、用户名、聊天内容）除非功能明确需要且用户知道；
  • 不静默下载可执行内容。

11.3自检（self-test）：常驻回归

给插件加一个环境变量开关的自检：装载时把核心行为自动跑一遍，结果写日志。 用户报告问题时，让他设环境变量重启宿主就能拿到诊断输出：

C# · 自检骨架
private void RunSelfTestIfRequested()
{
    if (Environment.GetEnvironmentVariable("MYPLUGIN_SELFTEST") != "1")
        return;

    _suppressSave = true;                        // 防污染三件套，见 7.4
    try { RunSelfTestBody(); }
    finally
    {
        _suppressSave = false;
        try { Settings = PluginSettingsFile.Load<MySettings>(_host!.PluginDirectory); }
        catch { }
    }
}

private void RunSelfTestBody()
{
    var results = new List<string>();

    // 例：改颜色 → 读回悬浮窗实际渲出来的颜色 → 必须一致
    Settings.IdleTextHex = "#FF0000";
    ApplySettings();
    var seen = _overlay?.TextColorAt(0);
    results.Add(seen == "#FF0000" ? "✓ 文字色生效" : $"✗ 文字色：期望 #FF0000，实际 {seen}");

    // 例：改大小 → 量悬浮窗实际尺寸
    // …更多用例…

    foreach (var line in results) _host!.Log("[自检] " + line);
    _host!.Log($"[自检] {results.Count(r => r.StartsWith("✓"))}/{results.Count} 项通过");
}

要点：只推进度/改参数，不重建结构；每个用例「改 → 读实际效果 → 断言」； 读不到实际效果的断言没有意义（「设置写进去了」不算验证，「悬浮窗真的变红」才算）。

11.4诊断钩子：「路径死了」的判别法

怀疑某条代码路径不被调用时（例如彩色循环不变色）：加调用计数 + 环境变量开关，跑一会儿看数字——

C#
private static int _diagApplyCalls;      // 诊断钩子（验证完删除）
private static bool DiagEnabled =>
    Environment.GetEnvironmentVariable("MYPLUGIN_DIAG") == "1";

private void ApplyColors()
{
    if (DiagEnabled) _diagApplyCalls++;
    // …原逻辑…
}
💡
口诀：计数冻结不涨 = 这条路径死了。KeyDisplay 的「彩色循环固定色」bug 就是这样定位的—— 高频刷新路径里边框刷色函数的调用数停在 7（建树时的格子数），再不增长，说明循环期间根本没人调它。 验证完把钩子删干净，别留在正式版里。

11.5UI 快照：离屏渲染页面成 PNG

排版问题（控件挤、边框吃内容）光看 XAML 看不出来。设环境变量把配置页渲成 PNG 存到插件目录， 自己打开看：

C# · 核心：把宿主主题字典并进来再渲
private void RunUiSnapshotIfRequested()
{
    if (Environment.GetEnvironmentVariable("MYPLUGIN_UI_SNAPSHOT") != "1") return;

    var page = new MyPage(this);

    // 关键：宿主主题字典挂在主窗口的 Resources 上，离屏渲染的页面取不到，
    // 不并进来渲出来就是一堆没样式的裸控件。
    var main = Application.Current?.MainWindow;
    if (main is not null)
        foreach (var dict in main.Resources.MergedDictionaries)
            page.Resources.MergedDictionaries.Add(dict);

    // 背景也取宿主的（取不到再兜底白色）
    Brush background = Brushes.White;
    try { if (main?.TryFindResource("WindowBgBrush") is Brush found) background = found; }
    catch { }

    var frame = new Border
    {
        Background = background,
        Padding = new Thickness(24, 20, 24, 20),
        Child = page,
    };

    const double width = 960;
    frame.Measure(new Size(width, double.PositiveInfinity));
    frame.Arrange(new Rect(0, 0, width, frame.DesiredSize.Height));
    frame.UpdateLayout();

    // 渲 PNG 存到插件目录，自己打开目视核对排版
    var w = (int)width;
    var h = (int)Math.Max(1, frame.DesiredSize.Height);
    var rtb = new RenderTargetBitmap(w, h, 96, 96, PixelFormats.Pbgra32);
    rtb.Render(frame);
    var encoder = new PngBitmapEncoder();
    encoder.Frames.Add(BitmapFrame.Create(rtb));
    using var fs = File.Create(Path.Combine(_host!.PluginDirectory, "page-snapshot.png"));
    encoder.Save(fs);
    _host.Log("[快照] 已渲染 page-snapshot.png");
}
⚠️
离屏渲染不会触发 Loaded——依赖 Loaded 的初始化（量尺寸、订阅）要手动补调一次， 否则快照上看到的是兜底状态，跟真实 bug 长得一样，没法区分。

12常见坑速查（实战版）

每一条都有出处。写插件前扫一遍，能省一半调试时间。

#坑症状 / 解法
1StaticResource 引宿主资源 页面白屏、装载即异常。插件页面运行期才挂进宿主树，StaticResource 提前解析必炸。 全部换 DynamicResource（铁律三）。
2变化回调没配 _loading 闸门 打开页面瞬间配置被 UI 旧值覆盖；或「保存→回填→保存」死循环。所有 TextChanged / ValueChanged / SelectionChanged / Checked 第一行 if (_loading) return;（7.3）。
3自检污染用户配置 反复跑自检后用户的缩放/颜色被探针值刷掉。三件套：_suppressSave 总闸 + try/finally 还原 + 结束后从磁盘重载（不是保存——中途炸掉时保存反而落盘脏值）（7.4）。
4Button 样式套到 ToggleButton 静默失效长成默认样子，不报错。样式强类型，ToggleButton 用 SmallPrimaryToggleButtonStyle 或自写（6.5）。
5PasswordBox / ListBox 不套样式 PasswordBox 没有隐式样式，必须显式 ModernPasswordBoxStyle； ListBox/TextBox/ComboBox/Slider/CheckBox 有隐式样式，不写 Style 直接用（6.1）。
6ContextMenu / Popup 弹出层没颜色 弹出层不在页面资源树里，DynamicResource 取不到宿主键 → 白底黑字或透明。 弹出层内部显式给颜色（Background="#FFFFFF" 这类写死，或代码里 TryFindResource 取到手再赋）。
7嵌套滚动抢滚轮 插件页面在宿主 ScrollViewer 里，自己的 ListBox 不设 MaxHeight 会被撑无限高/吃滚轮。 短列表自然展开，长列表设 MaxHeight（6.11）。
8ShowActivated="False" 就以为不抢焦点 只在第一次显示可靠。必须 SourceInitialized 里打 WS_EX_NOACTIVATE（8.3）。
9IsHitTestVisible=False 就以为穿透 只管 WPF 命中测试，系统层面窗口仍可点，全屏游戏光标现形。真穿透 WS_EX_TRANSPARENT（8.4）。
10宿主最小化悬浮窗跟着没了 WPF 的 ShowInTaskbar=False 靠隐藏所有者实现，而悬浮窗恰恰要无主。清 GWLP_HWNDPARENT + WS_EX_TOOLWINDOW（8.5）。
11改阴影参数内容漂移 窗口=内容+留白，留白随阴影变。位置按内容左上角记，留白反向补（8.7）。
12高 DPI 屏悬浮窗跑出屏幕 保存的裸坐标在新 DPI 下越界。摆位后 SystemParameters.WorkArea 夹取（8.8）。
13频繁 Hide()/Show() 悬浮窗 z-order 重排扰动游戏。窗口常驻，隐藏用 Opacity=0 + 强制穿透（8.6）。
14ColorDialog 的三个坑 插件上下文里能弹（宿主内置模块就用它）—— 但要全限定名防 CS0104 撞名、 返回的 A 恒 255 得拼回原透明度、并留自绘窗兜底（网易云歌词插件踩过调不起来的坑）（6.9）。
15UseWindowsForms 开了之后一堆 CS0104 System.Drawing / System.Windows.Forms 隐式 using 与 WPF 的 Brush/Point/MouseEventArgs 撞名。 csproj 里 <Using Remove="System.Drawing"/><Using Remove="System.Windows.Forms"/>， 用时写完全限定名（1.2）。
16编译过了以为 XAML 没问题 页面是运行期构造的，绑定/资源问题编译期不暴露。Initialize 里 new 一遍做预检（11.2）。
17宿主运行中覆盖 dll 失败 「文件正在使用」。先关宿主再拷贝再开（10.4）。
18ChatLineReceived 里做重活 宿主 UI 线程触发，卡整个程序。重活 Task.Run，回来 Dispatcher.Invoke（9.4）。
19每帧整树 Rebuild 40ms 定时器里重建视觉树 → 卡顿。分层：结构变化才 Rebuild，参数变化走轻刷新， 连续动画只改颜色（9.4，KeyDisplay 的 Rebuild / ApplyAppearance / SetCycleProgress 三层）。
20Shutdown 不幂等 / 不收尾 禁用后定时器还在跑、悬浮窗还在飘。_shutdown 闸门 + 全量收尾（3.2 / 8.9）。
21多个 DispatcherTimer 刷新节奏打架 两个定时器干同一件事，节奏错峰导致视觉抖动。一个时间轴一个 timer， 开关/改速绝不重置它的基准（KeyDisplay 的 _cycleStart 教训）。
22动画共享画刷被污染 对 DynamicResource 解析出的共享 Brush 做 ColorAnimation，会污染所有用到它的控件。 给要动画的元素套独立图层（Opacity 动画一个覆盖 Border），别动共享画刷本身。
23设置默认值随便给 Load 的默认值就是用户首体验。0.5 缩放、0 号字这类默认值等于开箱即坏（7.1）。
24Capabilities 含糊 安装确认框是知情同意。写「读取聊天消息」「GetAsyncKeyState 轮询」这种用户能懂的话； 用了钩子就写「安装 WH_KEYBOARD_LL 钩子只读按键状态，不拦截不记录」，别含糊（9.1 / 9.2）。
25钩子回调里 return 1 / 忘 CallNextHookEx 吞掉全系统按键，用户机器直接没法打字。按键显示只观察，最后一行必须是 CallNextHookEx 放行（9.2.2 ⑥）。
26钩子委托没存字段 交给系统的是函数指针，托管侧没强引用会被 GC 回收；回收后回调指向野地址， 进程直接崩。委托一定要存成字段（9.2.2 ①）。
27钩子回调里做耗时操作 系统给 300ms 超时，超时一次 Windows 静默摘掉钩子且不通知 —— 表现是「用着用着突然不亮了」，查不出报错。回调里只写状态位（9.2.2 ⑤）， 另外加个探活重装（9.2.2「被静默摘掉怎么办」）。
28只装了键盘钩子，没装鼠标 WH_KEYBOARD_LL 和 WH_MOUSE_LL 是两个独立钩子。 漏了鼠标的表现很具体：游戏里键盘亮、鼠标不亮（桌面场景能降级轮询所以看不出问题）。 键位显示这种要显示鼠标键的插件必踩（9.2.1 / 9.2.2「鼠标钩子」）。
29在后台线程装钩子 低级钩子靠宿主线程的消息循环派发回调。在纯后台线程上装会「装成功但 永远收不到回调」。要在本进程 UI 线程装（9.2.2 ②）。
30Shutdown 没卸钩子 比没停定时器严重得多 —— 宿主关了它还在跑，全系统按键都要过一遍你的回调。 卸载路径必须幂等（9.2.3 / 3.2）。
31切了钩子但没提权 绝区零这类提权进程的按键受 UIPI 保护，宿主不提权就依然读不到 —— 表现是「换了钩子还是没反应」。设置页要把这条写给用户，并实时显示当前是否已提权（9.2.1）。
32悬浮窗拖出屏幕外 DragMove() 随便拖出屏，出界位置还存盘。 自绘拖动 + 每帧 ClampToVirtualScreen（用 VirtualScreen，多显示器安全）， 尺寸变化/分辨率变化也要钳（8.10）。
33悬浮窗 OBS 抓不到 两个独立原因：WS_EX_TOOLWINDOW 被 OBS 窗口枚举过滤（列表里根本不出现， 宿主聊天窗没设它所以一直能看到）；AllowsTransparency 分层窗口 BitBlt 抓出来黑屏 （OBS 切 WGC 捕获即可）。前者加「OBS 直播模式」开关动态摘 TOOLWINDOW， 代价是窗口会出现在任务栏和 Alt+Tab（8.5）。

14AI 开发检查清单

架构与引用

  • csproj 只引用 Abstractions（ProjectReference 或 Compile Include），没有引用主程序 exe
  • plugin.json 的 apiVersion = 1，id 形如「作者名.插件名」且与 IPlugin.Id 一致

  • Shutdown 幂等（_shutdown 闸门），关窗口、停定时器、退订事件全覆盖
  • Initialize 里所有 IO/网络/反射都有 try/catch + host.Log，失败不静默
  • 自绘页面做了 new 预检（11.2）

界面

  • 样式引用全部 DynamicResource，零 StaticResource 指向宿主键
  • TextBox/ComboBox/Slider/CheckBox/ListBox 直接裸用（隐式样式）；带键样式从第 6 章抄，没自造视觉
  • ToggleButton 没有套 Button 样式（TargetType 陷阱）
  • ContextMenu / Popup 内部显式给色
  • 每个变化回调（TextChanged/ValueChanged/SelectionChanged/Checked）第一行有 if (_loading) return;
  • 程序回填 UI 用 try/finally 落闸（7.3）

悬浮窗（如有）

  • SourceInitialized 里打了 WS_EX_NOACTIVATE（XAML 的 ShowActivated=False 只是第一道）
  • 穿透用 WS_EX_TRANSPARENT；「拖动定位」开关负责临时关穿透
  • 清了所有者（GWLP_HWNDPARENT）+ WS_EX_TOOLWINDOW 不进任务栏
  • 窗口常驻，隐藏用 Opacity=0 + 强制穿透，没有反复 Hide/Show
  • 位置存「内容左上角」，阴影留白有补偿；摆位做 WorkArea 夹取
  • 动了其他窗口层级后调用 host.ReassertOverlayTopmost()

配置

  • 配置类默认值 = 合理首体验（不是 0/空）
  • 保存走防抖（ScheduleSave），没有每事件立即写盘
  • 自检/探针有防污染三件套（_suppressSave + try/finally + 磁盘重载）

行为与红线

  • 输入捕获：默认轮询；用了钩子的话，回调只读不吞（必 CallNextHookEx）、整段 try/catch、有超时意识（回调里不取锁不做 IO）、有探活重装（9.2）
  • 用了钩子的话，capabilities 如实声明「安装了 WH_KEYBOARD_LL，只读状态、不拦截、不记录」，并说明需要提权
  • 用了钩子的话，Shutdown 一定卸掉（幂等），切回轮询路径对称
  • 没有注入游戏进程、没有 mod/Forge 类侵入
  • ChatLineReceived 处理器里没有耗时操作（有就 Task.Run）
  • Capabilities 如实描述了读什么、联什么网
  • 定时器只有一个时间轴，开关/改速不重置基准
